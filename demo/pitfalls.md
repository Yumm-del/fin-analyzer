# 踩坑记录 — AI 金融分析 Agent

> 面试时被问「项目中遇到过什么困难」，这篇就是你的答案库。
> 每个坑都按 STAR 法则组织：情境 → 任务 → 行动 → 结果。

---

## 坑 1：网络搜索在国内全部不可用

**情境**：v0.1 用 `duckduckgo_search` 库做实时搜索，测试时三个搜索线程全部报错 connection reset。

**诊断**：看了报错 URL 才发现，这个库底层走的是 Bing（bing.com），而 Bing 在国内不稳定。换了直连 DuckDuckGo HTML 端点，三个备用域名也全部被墙。

**解决**：设计了「优雅降级」机制——搜索失败不报错退出，而是用 LLM 训练知识替代，并在报告中标注「以下分析基于 AI 训练知识，可能存在时效性不足」。核心功能不因一个外部依赖出问题就全挂。

**面试要点**：这是典型的生产环境容错思维——外部服务不可用时要有 fallback，不能把鸡蛋放一个篮子里。

---

## 坑 2：LLM 偶尔编造不存在的财务数据（幻觉）

**情境**：早期版本没有严格约束，LLM 有时会自信地列出一个完全不对的营收数字。

**解决**：
- System prompt 中加了「绝不编造数据」的硬约束
- 要求每条事实必须标注来源（搜索结果的 URL）
- 搜索不到的信息必须写「公开信息中暂未查到」
- 没有来源就没有数据——这是 prompt 工程里的「防幻觉三板斧」

**面试要点**：这体现了对 AI 产品核心痛点的理解——幻觉问题不是技术 bug，是产品设计问题。怎么让 AI 在不确定时说「不确定」，比让它变聪明更难。

---

## 坑 3：输出格式每次都不一样（一致性）

**情境**：同样的公司，问两次得到的报告结构完全不同——第一次先写风险，第二次先写公司概况。

**解决**：在 system prompt 中嵌入了一个精确的 Markdown 模板（四个固定模块 + 表格 + 分点格式），LLM 严格遵守。这就像给了 AI 一个「答题卡」而不是「问答题」。

**面试要点**：产品经理的核心工作之一就是把模糊需求变成结构化输出。这个 prompt 模板跟写 PRD 里的验收标准是一个道理。

---

## 坑 4：搜索耗时太长，用户等待体验差

**情境**：串行做三次搜索要 9 秒以上，终端用户容易以为程序卡死了。

**解决**：`concurrent.futures.ThreadPoolExecutor` 多线程并行搜索，耗时约等于最慢的那个（~3 秒）。每个搜索线程独立，一个挂了不影响其他。

**面试要点**：产品经理不光要考虑功能对不对，还要考虑体验好不好。并行搜索本质上跟「前端异步加载」是同一个用户体验原则。

---

## 学到了什么

1. **AI 产品不是 prompt 写好就完了**——要考虑网络挂了怎么办、LLM 说谎怎么办、输出不稳定怎么办
2. **优雅降级是 AI 产品的必修课**——大模型服务本身也可能挂，要有预案
3. **约束比能力更重要**——一个「不乱说的 AI」比一个「什么都说但经常错的 AI」更有价值
